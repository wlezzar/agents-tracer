# Architecture

agents-tracer is one Node package with no runtime dependencies. Its source is in layers, each a directory of `src/`, and the layers depend on each other in one direction: an adapter turns an agent's transcripts into the neutral model, the analysis charges time over that model, the conversation cuts what the transcripts said into the analysis's turns, and the report, the view, the server, and the CLI present them. Only the adapters know any agent.

## Layers

| Layer           | Holds                                                                                                                                                                                                                                                                             | May import                                                  |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `model`         | The neutral types: events, conversation entries, tool calls and descriptions, transcripts, sessions, session summaries, the adapter interface. Types only.                                                                                                                        | nothing                                                     |
| `util`          | Pure helpers shared by the layers: `fmt`, `kTok`, `pct`, `two`, `clock`, `day`, `spansDays`, `oneLine`, `table`, `indent`, `shellKey`, `commandKey`, `SUBCOMMAND_TOOLS`, and narrowing parsed JSON (`parseJsonLines`, `isRecord`, `stringOr`, `numberOr`, `jsText`, `looseText`). | nothing (`node:path` only)                                  |
| `adapters/<id>` | One agent's adapter: where its transcripts live, how its records map to events, how its tools read.                                                                                                                                                                               | `model`, `util`; any Node built-in                          |
| `adapters`      | `registry.ts`: `createRegistry`, and `registry`, the shipped adapters.                                                                                                                                                                                                            | `model`, every adapter                                      |
| `analysis`      | `analyzeTranscript`, the timing state machine over a transcript's events; `analyzeSession`, which also places each agent; and the aggregates the report and the view share.                                                                                                       | `model`, `util`                                             |
| `report`        | The text report: `report` (the summary, the subagents, the timeline), `sessionList`.                                                                                                                                                                                              | `analysis`, `model`, `util`                                 |
| `conversation`  | `buildConversation`, a session's conversation in threads and turns, `findingsOf`, what looks worth improving in each thread, and `markdown`, its Markdown export.                                                                                                                 | `analysis`, `model`, `util`                                 |
| `view`          | `ViewData`, `ConversationData`, `IndexData`, and `ProjectsData`, the JSON the viewer reads (`types.ts`, which the client shares), the builders of the first two (`buildView`, `viewSession`, `viewConversation`), and `renderHtml`.                                               | `analysis`, `conversation`, `model`, `util`; Node built-ins |
| `viewer`        | `template.html`, the viewer's markup and CSS, and `client/`, its browser TypeScript.                                                                                                                                                                                              | the client: `view` types only (`import type`)               |
| `server`        | The loopback HTTP server that serves a store's index of sessions and each session's pages, or every project of a root.                                                                                                                                                            | `view`, the registry, `model`, `util`; Node built-ins       |
| `cli`           | Argument parsing (`node:util` `parseArgs`), the commands, and the help.                                                                                                                                                                                                           | everything                                                  |

`eslint/layers.mjs` enforces the table as the ESLint rule `agents-tracer/layers`, configured by the `layers` map in `eslint.config.mjs`: imports between layers, the Node built-ins each layer may use, no file outside `src/`, and no package; a dynamic `import()` must name its module by a plain string, so that the rule can check it, and `src/` may not use `createRequire`. Pure layers (`model`, `util`, `analysis`, `report`, `conversation`) may not touch `process`, `Buffer`, or `console`, directly or through `globalThis`. Tests may import across layers.

The adapter boundary is enforced apart from the layers, from each adapter's vocabulary in `eslint/boundaries.mjs`: outside `src/adapters/*/`, ESLint's `no-restricted-syntax` refuses an agent's words (tool names unlikely to be ordinary words, file names, record fields) in TypeScript literals and object keys, and its tool names wherever a value is matched against one; `test/boundaries.test.ts` refuses the words in the other files of `src/` and checks that every shipped adapter has an entry naming every tool it knows.

## Data flow

```text
transcript files ──adapter.load──▶ Session ──analysis──▶ analyzed transcripts ──┬─▶ report ──▶ stdout
                                                                                ├─▶ view ──▶ ViewData ──renderHtml──▶ HTML ──▶ file or server
                                                                                └─▶ conversation ──┬─▶ markdown ──▶ stdout or file
                                                                                                   └─▶ view ──▶ ConversationData ──renderHtml──▶ HTML
adapter.listSessions ──▶ SessionSummary[] ──▶ report's list, or the server's index page
adapter.listStores ──▶ StoreSummary[] ──▶ the server's projects page under serve --all
```

1. The CLI picks an adapter from the registry (`--adapter`, default `claude-code`) and a store (`--store`, default `adapter.defaultStore(cwd, home)`).
2. `adapter.resolve(store, ref)` turns a session id, an id prefix, a subagent id, or a path into a transcript file; `adapter.load(path, options)` reads it into a `Session`: the main transcript, its subagents' transcripts, and the groups they ran in. Tool calls arrive with their `ToolDescription` filled in.
3. The analysis sorts each transcript's events by time and walks them ([model.md](model.md)), producing buckets, segments, model calls, tool calls, turns, and timeline items; a session's analysis also links each agent to the transcript that launched it.
4. The report renders the analysis as text. The view builds `ViewData`, one lane per transcript, and `renderHtml` embeds it in the built viewer, which the CLI's `html` writes to a file and the server serves.
5. For the conversation, `load` is given `{ conversation: true }`, and the adapter also reads each transcript's `conversation` (see [model.md](model.md#the-conversation)); `buildConversation` cuts it into the analysis's turns, and the CLI's `transcript` renders it as Markdown, or the view builds `ConversationData` for the conversation page.

## The conversation

`src/conversation/` turns an analyzed session into a `Conversation` (`types.ts`): plain, JSON-ready data that the view embeds as it is and that `markdown` writes out.

- `buildConversation(sessionAnalysis)`: the session, `shellLabel`, and one `Thread` per transcript, the main one first and the agents' by start (as the timeline's lanes, by the same ids), each with where it was launched (`parent`, `launcher`: the thread and the tool call), the group of agents it ran in (`group`), its state track (`segments`, the analysis's, as the timeline's lane has them), its stats (the analysis's times and counts, plus failed and refused calls, the peak context, and the harness's context items with their estimated tokens), and its turns. A transcript's entries are its `conversation`, or, from an adapter that reads none, what its events say (`entriesOf`), so every adapter gets a conversation page. The `Conversation`'s `groups` (`ThreadGroup`) are the session's groups its threads ran in, by their first agent's start, each with its summary and the thread and tool call that started it (the first whose result names the group).
- Turns: each prompt entry starts the next turn, numbered as the analysis's; entries before the first are turn 0. A turn's `active` time is the analysis's turn's, taken when the analysis's turn of that number started the same way.
- A model call (`ModelItem`) merges its records, as the analysis's `ModelCall` does by `messageId`, and takes its timing, usage, and stop reason from that call: `context` is the tokens it read (input, cache reads, and cache writes; none for a synthetic call), `out` its output tokens when the transcript's usage is known. A tool call (`ToolBlock`) sits in its call's blocks with its result beside it, its `status` (`ok`, `error`, `interrupted`, `pending`), its permission, its estimated output tokens, and the thread of the agent it launched. A result for a call the thread did not ask for is a `ResultItem`.
- Estimated tokens (`estimateTokens`, in `util`) are four characters a token: enough to compare what fills the context. The model calls' `context` is what the agent recorded, with its `cacheRead` and `cacheWrite`.
- Requests: a model call's `request` is the `RequestInfo` of its records (its shape's id and settings), the `Conversation`'s `shapes` are the transcripts' `requestShapes` that a thread used, each once and with its estimated tokens (`systemTokens`, and `toolTokens`, the tools that are not deferred), and a thread's `shapes` (`ThreadShape`) name the ones its calls used, in order, with how many calls and the first.
- Findings (`findings.ts`, `findingsOf`): each thread's `findings`, leads on what in the harness cost tokens, time, or the person's attention, one `Finding` per kind (a repeated harness text is one per text, its costliest four apart), with a `severity` (`high`, `medium`, `low`), a title, a detail, the tokens it cost when that is known, and every place it happened (`FindingRef`: the turn, the item's index in it, and the tool call). The kinds: a failed call made again unchanged with nothing written or run in between (`retry`); interrupts; API errors; refused calls; failed file edits; the prompt cache rebuilt without a pause (`cache-miss`, a call that read from the cache less than half of what the call before held, by 10k tokens or more) or after one of five minutes or more (`cache-lapse`); the system prompt or tools changing between calls; a file read again with the same input while unchanged (`repeated-read`, from two); tool outputs of 10k estimated tokens or more; the same harness text added again before a compaction (`repeated-context`); compactions; the context growing by 25k tokens or more in one step, with what came in; harness items of 5k tokens or more; tools never called whose definitions come to 1k tokens or more; and tool calls of two minutes or more that are not an agent's, a workflow's, or a question.
- `markdown(conversation, { context, maxOutput, subagents, turn, findings, setup })`: a header with the main thread's numbers, then the findings of the threads it writes (unless `findings` is false; in `turn`'s places only, for the main thread), then each thread (`## Main session`, `## Agent: …`) with a line on what its calls were sent with and its system prompt and tools (in full under `setup`, each shape once), each turn (`###`), each prompt, model call, harness stretch, compaction (`####`), and each tool call (`#####`). Prompts, replies, and reasoning are block quotes, so that their own headings stay inside them; inputs, outputs, and context are fenced with more backticks than they hold, and clipped to `maxOutput` characters, head and tail (3000 by default, 0 for all). The harness's context is one line per item unless `context`; `turn` keeps one turn of the main thread and the agents it launched.

## The report

`src/report/` renders an analysis as the prototype's text, byte for byte. `report(sessionAnalysis, options)` is what `agents-tracer report` prints: `summary` of the main transcript (its header, where the time went, the shell breakdown, the slowest tool calls and model responses, the turns), then `subagentReport` (the agents on their own, then each group under a header of its `kind`, name, id, and summary), then, with `timeline: true`, `timeline` (every turn, or only `turn`). `sessionList(summaries)` is what `agents-tracer list` prints.

A `ReportContext`, decided once from the main transcript, holds what the prototype kept in module-level variables: whether clock times carry their date (the main transcript spans local days, `spansDays`), whether model calls show their output tokens (`usageKnown` of the main transcript's calls), and `top`. The report reads tools by category through the analysis's aggregates and names the shell breakdown after `Session.shellToolName` (`Shell` when the agent has none); a missing time prints as the prototype's invalid date, `NaN:NaN:NaN`.

## The CLI

`src/cli/main.ts`, the `agents-tracer` bin, calls `run(argv, io, adapters)` (`run.ts`) with the process's working directory, home, and console; tests call `run` in process with their own IO and registry (`test/support/cli.ts`).

1. `parseCommand` (`args.ts`) reads the command line with `parseArgs` in its non-strict mode, keeping its tokens, and checks them itself so each mistake has a one-line message: the command (`list`, `report`, `html`, `transcript`, `serve`), the options it takes besides the global ones (`--adapter`, `--store` or its alias `--project`, `-h`/`--help`, `--version`), that each option has a value or none as it should (a value that starts with `-` only inline, `--out=-x.html`, since `--store --timeline` most likely forgot the store's), numbers (`--top`, `--max-output`, and `--port` whole, `--turn` from 1, `--min-idle` in seconds as a plain decimal such as `30`, `2.5`, or `.5`; no negative numbers, fractions of a count, or exponents, which the prototype ran with), and how many arguments. `--help` and `--version` win over everything else, even when an option took them for its value; no command prints the help.
2. `run` picks the adapter (`--adapter`, else the registry's default) and the store (`--store`, else `adapter.defaultStore(cwd, home)`), and runs the command. Relative paths (`--store`, a transcript's path as the session, `--out`) are read from `CliIo.cwd`; when that is the process's working directory, as for the `agents-tracer` bin, a path stays as it was typed in what the CLI prints and the page embeds, as the prototype's does, and otherwise (in-process tests) it is resolved against `cwd`, and a relative session that names no file there is read as an id only. `report` resolves the session, loads it, analyzes it (without its agents under `--no-subagents`), and prints `report`; `list` prints `sessionList` of `adapter.listSessions`; `html` resolves and loads the session, renders `viewSession` of it into the built viewer, writes it to `--out` (relative to the working directory) or to `defaultHtmlPath` (`agents-tracer/html/<transcript id>.html` under `$XDG_CACHE_HOME` when it is an absolute path, else under `~/.cache`), and prints `Wrote <path> (<size>K)`; with `--conversation`, it loads the session with its conversation and writes `viewConversation` of it instead, by default to `<transcript id>.conversation.html`; `transcript` loads the session with its conversation, builds it (without its agents under `--no-subagents`), checks that `--turn` names a turn the session has, and prints `markdown` of it, or writes it to `--out` and prints `Wrote <path> (<size>K)`; `serve` checks that the store exists, starts the server, and prints `Serving <store> on http://127.0.0.1:<port>/` (the port the system picked for `--port 0`); with `--all` (which `--store` and `--project` conflict with), it checks that the adapter's root, `adapter.defaultRoot(home)`, is a directory (else `no projects at <root>`), serves it, and prints `Serving every project in <root> on http://127.0.0.1:<port>/`.
3. Everything `run` prints goes through util's `printable`, which shows every control character but a newline or a tab as a visible stand-in of the same length (`␛` for ESC): titles, prompts, model text, and commands can hold text from anywhere, fetched pages included, and none of it may drive the terminal. Any error prints `agents-tracer: <the first line of its message>` to standard error, and the exit code is 1. A store that does not exist says so; the adapter's resolve errors (no match, or how many matched) are printed as they are; so is a viewer that is not built, and a port that is taken.

`env.ts` reads `AGENTS_TRACER_SUBCOMMAND_TOOLS`, the person's tools whose subcommand keys a shell command beyond util's `SUBCOMMAND_TOOLS`, into the `subcommandTools` that `run` passes to `adapter.load`, the report, the view, and the server alike.

`run` is asynchronous: for `serve` it returns once the server listens, and the server keeps the process running until it ends, or until `CliIo.signal` aborts (the tests' way to stop it). `CliIo` also carries the environment (`env`) and, for tests, `viewer`, a stand-in for the built viewer's page (`test/support/cli.ts` passes a minimal page holding the data placeholder, so in-process tests need no build).

## The view

`src/view/` turns an analyzed session into `ViewData` (`types.ts`), ported from the prototype's `lane` and `buildView` so that the JSON holds every field and value the prototype's does (`pnpm parity` compares them over every local transcript, and `test/view-fixtures.test.ts` over the fixtures):

- `buildView(sessionAnalysis, { serve?, now? })`: the session (`id`, `title`, `cwd`, `file`); the groups of lanes (`main`, the session's own; `agents`, the agents on their own; one per `Group` of the session, with its summary), the session first and the others by their first lane's start; and one lane per transcript, the main transcript's first and the agents' by start, each with its state track (`seg`, the analysis's segments), its spans (tool calls and model calls by start, with the prototype's tie order; a model span lists its tool calls' span indexes), its turns, its buckets largest first, its shell breakdown (`bash`), and its stats. Texts are clipped to their head and tail (`clip`).
- `viewSession(session, options)` analyzes the session first; the server and the CLI call it.
- Beyond the prototype's fields, the data carries what lets the client read tools by category and name things the agent's way: `toolCategories` (each tool name's `ToolCategory`), `shellLabel` (`Session.shellToolName`, `Shell` without one), each tool span's `cat`, and each session group's `kind` (`Group.kind`, such as `Workflow`, which the detail pane names). The index page's data (`IndexData`) is the store, the adapter's `displayName` (`Claude Code sessions`), and the sessions, each with the `href` of its page (an addition: the prototype's client built the link itself), null for one the server cannot open; under `serve --all`, it also has `projectsHref`, the projects page, and `cwd`, the project's directory.
- The projects page's data (`ProjectsData`), which the prototype has not, is the root, the adapter's `displayName` (`Claude Code projects`), and one `ViewProject` per store of `adapter.listStores`: its id, its `cwd` (null when no session names one), the `href` of its index (null for an id the server cannot put in a URL), and its sessions (`ViewProjectSession`: the id, the size, the modification time, and the `href` and `conversationHref` of its pages, null when the project's or the session's id cannot be in a URL), for the page's search by id. The server builds it; `src/view/` only types it.
- Beyond the prototype's fields too, from the server only: `indexHref` (`ViewOptions.indexHref`, `ConversationViewOptions.indexHref`), where a session's timeline and conversation link back to: `/` for one store, `/p/<project>` for a project.
- Numbers the prototype computes as NaN (the wall time of a transcript without events, a group's first start) are `null`, as JSON writes them; a transcript without events has no `start` or `end`.
- Beyond the prototype's fields too, for the links to the conversation page: each span's `id` (the tool call's id, the model call's message id), and, from the server only, `conversationHref` (the session's conversation page) and each index session's `conversationHref`.
- `viewConversation(session, { serve?, timelineHref?, now?, maxText? })` builds `ConversationData`: the session's `buildConversation` with every text clipped to its head and tail beyond `CONVERSATION_TEXT` (100,000) characters, so that one huge output cannot swell the page, its build time, and, from the server, `serve` and `timelineHref`.

`renderHtml(data, template = viewerTemplate())` embeds the data in the built viewer; `viewerTemplate()` reads it, or throws `the viewer is not built … run pnpm build`.

## The viewer and how it is built

The viewer is one self-contained HTML file: markup and CSS from `src/viewer/template.html`, the client bundled into one inline script, and the view data embedded as JSON. The same file is the timeline, the conversation page, and the index: the template holds a root for each (`#app`, `#conversation`, `#index`), and the client shows the one its data asks for.

`pnpm build` runs `scripts/build.ts`, which:

1. empties `dist/` and runs `tsc -p tsconfig.build.json`, which emits `src/` (without tests and without the client) to `dist/`, and marks `dist/cli/main.js`, the `agents-tracer` bin, executable;
2. bundles `src/viewer/client/main.ts` with esbuild into one IIFE, refusing a bundle that holds `</script`, `<!--`, or the data placeholder;
3. replaces the template's `<!-- @viewer-client -->` marker with the bundle in a `<script>`, checks that the template holds the data placeholder `"__TRACE_DATA__"` exactly once (in `<script id="trace-data" type="application/json">`), and writes `dist/viewer/viewer.html`.

`renderHtml` reads `dist/viewer/viewer.html` relative to its own module (`import.meta.url`) and replaces `"__TRACE_DATA__"` with the view data's JSON, every `<` escaped as `\u003c` so that nothing in the data can end the script block, through a replacer function so that `$` sequences in the data are not read as patterns. The client reads the JSON from `#trace-data`, then draws the session index (when the data has `index`), a session's conversation (when it has `conversation`), or a session's timeline.

The client's TypeScript is checked by `src/viewer/client/tsconfig.json` (DOM, no Node types) and imports only types from `view/` (`view/types.ts`, which re-exports the model's and the analysis's types it needs), so the bundle holds the client alone. It is the prototype's script ported module by module, with the same behavior and the same pixels. Its pure logic lives apart from the DOM and canvas code, so that vitest tests it in Node:

Prettier leaves `template.html` alone: the markup and CSS are the prototype's, with two words made neutral (the shell filter's option and the index's heading, which the client fills in).

## The server

`src/server/` (`startServer`, `createHandler`) is what `agents-tracer serve [--port 4390] [--all]` runs. It listens on 127.0.0.1 only: transcripts hold everything the sessions saw. It serves one store (`ServerOptions.store`) or every project of a root (`ServerOptions.root`), and one function serves a store's pages under a URL prefix: `''` for the one store, `/p/<project>` for a project of the root. For one store, `GET /` serves the index page of the store's sessions (listed again on every request); `GET /s/<id>`, where the id matches `[\w-]+`, serves the viewer for that session (`serve: true`, so it links back to the index at `indexHref`, and `conversationHref`), and `GET /s/<id>/conversation` its conversation page (loaded with `{ conversation: true }`, with `timelineHref` and `indexHref`), each resolved through the adapter by id with `{ paths: false }` (never as a path from the URL) and kept, by the page, its prefix, the id it was asked for, and the session's path, until the adapter's `version` of the session changes (for Claude Code, the count, size, and newest modification time of the transcript and of every file under its `subagents/` and `workflows/`), or built on every request for an adapter without `version`. The kept pages are bounded: once their HTML holds more than `cacheChars` characters (`CACHE_CHARS`, 100 million, by default), the least recently used go first, and a page longer than that is not kept, so a server that runs for weeks does not keep every page it ever built. The index gives each session the `href` of its page and the `conversationHref` of its conversation, or null for an id that does not match `[\w-]+`, which the index lists without a link. An id that names no session is a 404 with the resolver's message; any other path is a 404; an error is a 500 with its message.

For a root (`serve --all`), `GET /` serves the projects page (`ProjectsData`, from `adapter.listStores(root)`, listed again on every request), whose projects link to `/p/<project>` when the project's id matches `[\w-]+`. `GET /p/<project>` (with or without a trailing `/`) serves the project's index, with `projectsHref` and `cwd`, and `GET /p/<project>/s/<id>` and `/p/<project>/s/<id>/conversation` its sessions' pages, with `indexHref` `/p/<project>`. The project is found by its id among `adapter.listStores(root)`, never by a path made from the URL, and an id the root has not is a 404, `no project "<id>" in <root>`. `GET /s/<ref>` and `/s/<ref>/conversation` try the ref in every store whose id can be in a URL, and redirect (302) to `/p/<project>/s/<ref>`, and its conversation, when exactly one store resolves it; otherwise they are a 404 that says the ref matches sessions in several projects or no single session or agent in any (a store's resolve also fails when the ref is a prefix of several of its sessions). Beyond the prototype's server, it refuses with a 403 a request whose `Host` is not `127.0.0.1`, `localhost`, or `[::1]` on some port (a rebound domain sends its own, so a web page cannot read the sessions, while a forwarded port still works), answers a method other than GET and HEAD with a 405, and sends every response with `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: DENY`. To reach it from another machine, forward the port over SSH (see the README).
