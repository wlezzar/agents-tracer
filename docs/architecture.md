# Architecture

agents-tracer is one Node package with no runtime dependencies. Its source is in layers, each a directory of `src/`, and the layers depend on each other in one direction: an adapter turns an agent's transcripts into the neutral model, the analysis charges time over that model, and the report, the view, the server, and the CLI present the analysis. Only the adapters know any agent.

## Layers

| Layer           | Holds                                                                                                                                                                                                                                                                             | May import                                            |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `model`         | The neutral types: events, tool calls and descriptions, transcripts, sessions, session summaries, the adapter interface. Types only.                                                                                                                                              | nothing                                               |
| `util`          | Pure helpers shared by the layers: `fmt`, `kTok`, `pct`, `two`, `clock`, `day`, `spansDays`, `oneLine`, `table`, `indent`, `shellKey`, `commandKey`, `SUBCOMMAND_TOOLS`, and narrowing parsed JSON (`parseJsonLines`, `isRecord`, `stringOr`, `numberOr`, `jsText`, `looseText`). | nothing (`node:path` only)                            |
| `adapters/<id>` | One agent's adapter: where its transcripts live, how its records map to events, how its tools read.                                                                                                                                                                               | `model`, `util`; any Node built-in                    |
| `adapters`      | `registry.ts`: `createRegistry`, and `registry`, the shipped adapters.                                                                                                                                                                                                            | `model`, every adapter                                |
| `analysis`      | `analyzeTranscript`, the timing state machine over a transcript's events; `analyzeSession`, which also places each agent; and the aggregates the report and the view share.                                                                                                       | `model`, `util`                                       |
| `report`        | The text report: `report` (the summary, the subagents, the timeline), `sessionList`.                                                                                                                                                                                              | `analysis`, `model`, `util`                           |
| `view`          | `ViewData`, the JSON the viewer reads (`types.ts`, which the client shares), its builder (`buildView`, `viewSession`), and `renderHtml`.                                                                                                                                          | `analysis`, `model`, `util`; Node built-ins           |
| `viewer`        | `template.html`, the viewer's markup and CSS, and `client/`, its browser TypeScript.                                                                                                                                                                                              | the client: `view` types only (`import type`)         |
| `server`        | The loopback HTTP server that serves the session index and each session's viewer.                                                                                                                                                                                                 | `view`, the registry, `model`, `util`; Node built-ins |
| `cli`           | Argument parsing (`node:util` `parseArgs`), the commands, and the help.                                                                                                                                                                                                           | everything                                            |

`eslint/layers.mjs` enforces the table as the ESLint rule `agents-tracer/layers`, configured by the `layers` map in `eslint.config.mjs`: imports between layers, the Node built-ins each layer may use, no file outside `src/`, and no package; a dynamic `import()` must name its module by a plain string, so that the rule can check it, and `src/` may not use `createRequire`. Pure layers (`model`, `util`, `analysis`, `report`) may not touch `process`, `Buffer`, or `console`, directly or through `globalThis`. Tests may import across layers.

The adapter boundary is enforced apart from the layers, from each adapter's vocabulary in `eslint/boundaries.mjs`: outside `src/adapters/*/`, ESLint's `no-restricted-syntax` refuses an agent's words (tool names unlikely to be ordinary words, file names, record fields) in TypeScript literals and object keys, and its tool names wherever a value is matched against one; `test/boundaries.test.ts` refuses the words in the other files of `src/` and checks that every shipped adapter has an entry naming every tool it knows.

## Data flow

```text
transcript files ──adapter.load──▶ Session ──analysis──▶ analyzed transcripts ──┬─▶ report ──▶ stdout
                                                                                └─▶ view ──▶ ViewData ──renderHtml──▶ HTML ──▶ file or server
adapter.listSessions ──▶ SessionSummary[] ──▶ report's list, or the server's index page
```

1. The CLI picks an adapter from the registry (`--adapter`, default `claude-code`) and a store (`--store`, default `adapter.defaultStore(cwd, home)`).
2. `adapter.resolve(store, ref)` turns a session id, an id prefix, a subagent id, or a path into a transcript file; `adapter.load(path, options)` reads it into a `Session`: the main transcript, its subagents' transcripts, and the groups they ran in. Tool calls arrive with their `ToolDescription` filled in.
3. The analysis sorts each transcript's events by time and walks them ([model.md](model.md)), producing buckets, segments, model calls, tool calls, turns, and timeline items; a session's analysis also links each agent to the transcript that launched it.
4. The report renders the analysis as text. The view builds `ViewData`, one lane per transcript, and `renderHtml` embeds it in the built viewer, which the CLI's `html` writes to a file and the server serves.

## The report

`src/report/` renders an analysis as the prototype's text, byte for byte. `report(sessionAnalysis, options)` is what `agents-tracer report` prints: `summary` of the main transcript (its header, where the time went, the shell breakdown, the slowest tool calls and model responses, the turns), then `subagentReport` (the agents on their own, then each group under a header of its `kind`, name, id, and summary), then, with `timeline: true`, `timeline` (every turn, or only `turn`). `sessionList(summaries)` is what `agents-tracer list` prints.

A `ReportContext`, decided once from the main transcript, holds what the prototype kept in module-level variables: whether clock times carry their date (the main transcript spans local days, `spansDays`), whether model calls show their output tokens (`usageKnown` of the main transcript's calls), and `top`. The report reads tools by category through the analysis's aggregates and names the shell breakdown after `Session.shellToolName` (`Shell` when the agent has none); a missing time prints as the prototype's invalid date, `NaN:NaN:NaN`.

## The CLI

`src/cli/main.ts`, the `agents-tracer` bin, calls `run(argv, io, adapters)` (`run.ts`) with the process's working directory, home, and console; tests call `run` in process with their own IO and registry (`test/support/cli.ts`).

1. `parseCommand` (`args.ts`) reads the command line with `parseArgs` in its non-strict mode, keeping its tokens, and checks them itself so each mistake has a one-line message: the command (`list`, `report`, `html`, `serve`), the options it takes besides the global ones (`--adapter`, `--store` or its alias `--project`, `-h`/`--help`, `--version`), that each option has a value or none as it should (a value that starts with `-` only inline, `--out=-x.html`, since `--store --timeline` most likely forgot the store's), numbers (`--top` and `--port` whole, `--turn` from 1, `--min-idle` in seconds as a plain decimal such as `30`, `2.5`, or `.5`; no negative numbers, fractions of a count, or exponents, which the prototype ran with), and how many arguments. `--help` and `--version` win over everything else, even when an option took them for its value; no command prints the help.
2. `run` picks the adapter (`--adapter`, else the registry's default) and the store (`--store`, else `adapter.defaultStore(cwd, home)`), and runs the command. Relative paths (`--store`, a transcript's path as the session, `--out`) are read from `CliIo.cwd`; when that is the process's working directory, as for the `agents-tracer` bin, a path stays as it was typed in what the CLI prints and the page embeds, as the prototype's does, and otherwise (in-process tests) it is resolved against `cwd`, and a relative session that names no file there is read as an id only. `report` resolves the session, loads it, analyzes it (without its agents under `--no-subagents`), and prints `report`; `list` prints `sessionList` of `adapter.listSessions`; `html` resolves and loads the session, renders `viewSession` of it into the built viewer, writes it to `--out` (relative to the working directory) or to `defaultHtmlPath` (`agents-tracer/html/<transcript id>.html` under `$XDG_CACHE_HOME` when it is an absolute path, else under `~/.cache`), and prints `Wrote <path> (<size>K)`; `serve` checks that the store exists, starts the server, and prints `Serving <store> on http://127.0.0.1:<port>/` (the port the system picked for `--port 0`).
3. Everything `run` prints goes through util's `printable`, which shows every control character but a newline or a tab as a visible stand-in of the same length (`␛` for ESC): titles, prompts, model text, and commands can hold text from anywhere, fetched pages included, and none of it may drive the terminal. Any error prints `agents-tracer: <the first line of its message>` to standard error, and the exit code is 1. A store that does not exist says so; the adapter's resolve errors (no match, or how many matched) are printed as they are; so is a viewer that is not built, and a port that is taken.

`env.ts` reads `AGENTS_TRACER_SUBCOMMAND_TOOLS`, the person's tools whose subcommand keys a shell command beyond util's `SUBCOMMAND_TOOLS`, into the `subcommandTools` that `run` passes to `adapter.load`, the report, the view, and the server alike.

`run` is asynchronous: for `serve` it returns once the server listens, and the server keeps the process running until it ends, or until `CliIo.signal` aborts (the tests' way to stop it). `CliIo` also carries the environment (`env`) and, for tests, `viewer`, a stand-in for the built viewer's page (`test/support/cli.ts` passes a minimal page holding the data placeholder, so in-process tests need no build).

## The view

`src/view/` turns an analyzed session into `ViewData` (`types.ts`), ported from the prototype's `lane` and `buildView` so that the JSON holds every field and value the prototype's does (`pnpm parity` compares them over every local transcript, and `test/view-fixtures.test.ts` over the fixtures):

- `buildView(sessionAnalysis, { serve?, now? })`: the session (`id`, `title`, `cwd`, `file`); the groups of lanes (`main`, the session's own; `agents`, the agents on their own; one per `Group` of the session, with its summary), the session first and the others by their first lane's start; and one lane per transcript, the main transcript's first and the agents' by start, each with its state track (`seg`, the analysis's segments), its spans (tool calls and model calls by start, with the prototype's tie order; a model span lists its tool calls' span indexes), its turns, its buckets largest first, its shell breakdown (`bash`), and its stats. Texts are clipped to their head and tail (`clip`).
- `viewSession(session, options)` analyzes the session first; the server and the CLI call it.
- Beyond the prototype's fields, the data carries what lets the client read tools by category and name things the agent's way: `toolCategories` (each tool name's `ToolCategory`), `shellLabel` (`Session.shellToolName`, `Shell` without one), each tool span's `cat`, and each session group's `kind` (`Group.kind`, such as `Workflow`, which the detail pane names). The index page's data (`IndexData`) is the store, the adapter's `displayName` (`Claude Code sessions`), and the sessions, each with the `href` of its page (an addition: the prototype's client built the link itself), null for one the server cannot open.
- Numbers the prototype computes as NaN (the wall time of a transcript without events, a group's first start) are `null`, as JSON writes them; a transcript without events has no `start` or `end`.

`renderHtml(data, template = viewerTemplate())` embeds the data in the built viewer; `viewerTemplate()` reads it, or throws `the viewer is not built … run pnpm build`.

## The viewer and how it is built

The viewer is one self-contained HTML file: markup and CSS from `src/viewer/template.html`, the client bundled into one inline script, and the view data embedded as JSON.

`pnpm build` runs `scripts/build.ts`, which:

1. empties `dist/` and runs `tsc -p tsconfig.build.json`, which emits `src/` (without tests and without the client) to `dist/`, and marks `dist/cli/main.js`, the `agents-tracer` bin, executable;
2. bundles `src/viewer/client/main.ts` with esbuild into one IIFE, refusing a bundle that holds `</script`, `<!--`, or the data placeholder;
3. replaces the template's `<!-- @viewer-client -->` marker with the bundle in a `<script>`, checks that the template holds the data placeholder `"__TRACE_DATA__"` exactly once (in `<script id="trace-data" type="application/json">`), and writes `dist/viewer/viewer.html`.

`renderHtml` reads `dist/viewer/viewer.html` relative to its own module (`import.meta.url`) and replaces `"__TRACE_DATA__"` with the view data's JSON, every `<` escaped as `\u003c` so that nothing in the data can end the script block, through a replacer function so that `$` sequences in the data are not read as patterns. The client reads the JSON from `#trace-data`, then draws either the session index (when the data has `index`) or a session.

The client's TypeScript is checked by `src/viewer/client/tsconfig.json` (DOM, no Node types) and imports only types from `view/` (`view/types.ts`, which re-exports the model's and the analysis's types it needs), so the bundle holds the client alone. It is the prototype's script ported module by module, with the same behavior and the same pixels. Its pure logic lives apart from the DOM and canvas code, so that vitest tests it in Node:

| Module                            | Holds                                                                                                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format.ts`                       | The viewer's `fmt`, `kTok`, `clock`, `dayStr`, `stamp`, `pct`, `oneLine` (an en dash for a missing value, the browser's short dates).                                                       |
| `categories.ts`                   | The colors (model, shell, other tools, and the kinds of waiting), a bucket's and a span's by category (`toolCategories`, `cat`), labels.                                                    |
| `timeMap.ts`                      | `buildPieces` (idle stretches of two minutes or more collapsed), `TimeMap` (real to display time and back), the viewport's clamp, fit, zoom, pan, zoom-to, and reveal, `Scale` (time to x). |
| `ticks.ts`                        | The axis's ticks on local round times, and `fitText`.                                                                                                                                       |
| `layout.ts`                       | `packRows` (model calls on row 0, tool calls packed from row 1), the lanes and group headers top to bottom, `hitTest`.                                                                      |
| `trace.ts`                        | The trace tab's rows: filters by kind, text, and range, the turns and idle stretches between them, and sorting.                                                                             |
| `data.ts`                         | Reads the embedded JSON and checks its shape.                                                                                                                                               |
| `app.ts`                          | The session's state and the actions the rest share: layout, mapping, viewport, sizing, drawing requests, selection, lanes, groups.                                                          |
| `draw.ts`                         | The axis, lanes, and overview canvases.                                                                                                                                                     |
| `interact.ts`                     | The tooltip, clicks, drag to pan, wheel and pinch, the axis brush, the overview's window, double click, and the keyboard (W, S, A, D, F, J, K, Escape, `/`).                                |
| `panels.ts`                       | The stats tiles, the Trace, Turns, Breakdown, and Agents tabs, and the detail pane with its copy buttons.                                                                                   |
| `indexPage.ts`                    | The server's index of sessions.                                                                                                                                                             |
| `theme.ts`, `colors.ts`, `dom.ts` | The theme (system, light, dark, kept in `localStorage`), the canvas colors read from the CSS, and building elements (text through `textContent` and attributes only).                       |

The client colors, filters, and names tools by category, never by name: the shell (`cat` `shell`) has its own color and filter, a question (`question`) is the person's time, the legend, the trace filter, and the breakdown say `shellLabel` where the prototype says `Bash`, and the detail pane labels a shell call's input `Command` by its category. Two prototype quirks are kept for the same pixels: the breakdown writes `null` for a section it leaves out (a lane without shell calls or without compactions shows `nullnull`), and a tool span's tooltip reads its output as a token count (` · <output> output tokens`). Each is marked in the code.

Prettier leaves `template.html` alone: the markup and CSS are the prototype's, with two words made neutral (the shell filter's option and the index's heading, which the client fills in).

## The server

`src/server/` (`startServer`, `createHandler`) is what `agents-tracer serve [--port 4390]` runs. It listens on 127.0.0.1 only: transcripts hold everything the sessions saw. `GET /` serves the index page of the store's sessions (listed again on every request); `GET /s/<id>`, where the id matches `[\w-]+`, serves the viewer for that session (`serve: true`, so it links back to the index), resolved through the adapter by id with `{ paths: false }` (never as a path from the URL) and kept until the adapter's `version` of the session changes (for Claude Code, the count, size, and newest modification time of the transcript and of every file under its `subagents/` and `workflows/`), or built on every request for an adapter without `version`. The index gives each session the `href` of its page, or null for an id that does not match `[\w-]+`, which the index lists without a link. An id that names no session is a 404 with the resolver's message; any other path is a 404; an error is a 500 with its message. Beyond the prototype's server, it refuses with a 403 a request whose `Host` is not `127.0.0.1`, `localhost`, or `[::1]` on some port (a rebound domain sends its own, so a web page cannot read the sessions, while a forwarded port still works), answers a method other than GET and HEAD with a 405, and sends every response with `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: DENY`. To reach it from another machine, forward the port over SSH (see the README).

## Tooling

- Node 24 and pnpm 12.6.0, pinned in `mise.toml` and `package.json`.
- TypeScript 6, strict, `NodeNext`, `verbatimModuleSyntax`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `erasableSyntaxOnly` (so `scripts/*.ts` run under Node's type stripping). `tsconfig.json` checks the Node code, tests, scripts, and configs; `tsconfig.build.json` emits; `src/viewer/client/tsconfig.json` checks the client and its tests; `test/e2e/tsconfig.json` checks the browser tests; `pnpm typecheck` runs all four but the emitting one.
- ESLint 10 with typescript-eslint's `strictTypeChecked` and `stylisticTypeChecked`, no type assertions (`consistent-type-assertions: never`), and the repository's rules in `eslint/`.
- Prettier 3 (`printWidth` 120, single quotes, trailing commas).
- vitest 5, in `Europe/Paris` so that local-time formatting is pinned; Playwright 1.63.0 for the viewer's browser tests (`pnpm test:e2e`: `vitest.e2e.config.ts` runs `test/e2e/` after a build, with its own `test/e2e/tsconfig.json`, which adds the DOM for the code the tests run in the page).
- esbuild bundles the viewer client.
- `scripts/parity.ts` (`pnpm parity`) compares the built CLI with the prototype over real transcripts, and `scripts/expectations.ts` writes the prototype's output for the fixtures that `test/report-fixtures.test.ts` compares the CLI with: see Parity in [AGENTS.md](../AGENTS.md).
